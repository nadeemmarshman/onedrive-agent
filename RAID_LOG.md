# OneDrive Agent — RAID Log

**Purpose:** Risks, Assumptions, Issues, and Dependencies tracked for this
project, as a standard PM control artifact — separate from `BACKLOG.md`
(which tracks Agile/Scrum-style delivery and process) and the handoff
document (which tracks agreed project state and standing rules). RAID
tracks *what could go wrong, what we're assuming, what has gone wrong, and
what we depend on* — complementary to, not a duplicate of, the other two.

Status values: **Open** (active, not yet resolved/mitigated) | **Closed**
(resolved, mitigated, or no longer applicable, with resolution noted) |
**Monitoring** (not currently active, but being watched)

## Issues

Things that **have already happened** and required resolution.

| # | Raised | Issue | Root cause | Resolution | Status |
|---|---|---|---|---|---|
| I1 | 2026-06-30 | `README.md` and `BACKLOG.md` were overwritten with one-line placeholder text (via `echo "..." > file`) instead of containing their real, previously-generated content, and this was committed and pushed to GitHub before being caught. | Combination of **Risk R2** (status drift between sessions) and **Assumption A1** (wrongly trusting a clean commit/push as proof of correct content) — the actual files on disk were placeholder versions at the time of commit, not the real ones generated earlier in the session. | Caught via the newly-adopted screenshot-verification rule, by noticing the commit's `84 deletions(-)` stat didn't match what should have been a pure-addition commit. Real files re-downloaded, re-saved locally, re-committed (`198 insertions(+), 2 deletions(-)` — correct signature this time), and verified directly via `git show HEAD:README.md` confirming the actual committed content, not just commit stats. | Closed — resolved 2026-06-30, verified by content inspection, not just commit success |
| I2 | 2026-06-26 | `pip install anthropic` failed during Phase 3 setup: the `tokenizers` dependency attempted to compile from Rust source, and no Rust compiler was present on the machine. | Python 3.14 is a very new release; a prebuilt wheel for `tokenizers` may not yet have been available for it at the time, causing pip to fall back to a source build. | Updated pip first (`python -m pip install --upgrade pip`), after which a prebuilt wheel installed cleanly without needing Rust. | Closed — resolved 2026-06-26 |
| I3 | 2026-06-30 | Confusion over which handoff document version (v3.0 vs v3.2) was actually loaded in Project knowledge, due to an intermediate swap that wasn't explicitly confirmed back in chat. | Same root cause as R2/A1 — reliance on verbal/remembered status rather than verified evidence. | Clarified via direct question and screenshot; correct version (v4.0) confirmed loaded via Project knowledge files panel screenshot. | Closed — resolved 2026-06-29/30 |
| I4 | 2026-07-02 | Phase 5 introduced destructive action execution for the first time — risk of acting on the wrong file or losing progress if the run is interrupted mid-execution with no audit trail. | Risk R6 (DR/rollback): no agent-managed record of what existed before the run. | Pre-run manifest snapshot (`pre_run_snapshot.json`) implemented as a hard precondition in `approval_gate.py`: if the snapshot cannot be written, all execution is blocked ("no snapshot, no actions"). Snapshot records path, size, MD5 hash, and modification timestamp for every affected file before any action executes. Proven in a live run (2026-07-02): snapshot written at `2026-07-02T08:02:47 UTC`, two duplicate `.txt` files correctly recorded with matching MD5 hashes confirming they were genuine duplicates. OneDrive recycle bin accepted as the primary file-recovery mechanism. | Closed — implemented and verified in live run |
| I5 | 2026-07-02 | `test_phase3_4_45.py`'s two Phase 5 integration tests (`test_integration_full_phase5_approve_all` / `_reject_all`) scanned and operated on the **real** `sample_data/` fixture folder rather than an isolated copy. Since `_execute_delete()` is not mocked in these tests, "approve all" genuinely deleted real fixture files on every test run — a self-inflicted, recurring bug that caused `sample_data/` to silently drift out of sync with what `test_phase2.py` expects (2 unit test failures: file count and duplicate-group size), which in turn caused the integration layer to be skipped entirely under the suite's own "skip integration if unit tests fail" rule. | Test isolation gap — no test in the suite created an independent copy of test fixtures before performing destructive operations on them. | Caught by an independent Claude Cowork peer review (2026-07-02) that actually ran the test suite rather than only reading the code, and diagnosed the exact root cause. Fixed by rebuilding both integration tests to copy `sample_data/` into a temporary directory (`tempfile.mkdtemp()`) via `shutil.copytree()`, operate entirely within that temp copy, and clean it up in a `finally` block — the real fixture folder is never touched. Verified: full 45-test suite re-run with fixture file hashes (MD5) confirmed byte-identical before and after the run. A secondary, related drift was also found and fixed during verification: the buggy test's file-recreation used `Path.write_text()` without a trailing newline, while the original fixture file (created via a shell `echo` command in Phase 1) has one — producing files with matching content but different bytes/hashes. Fixed by recreating the duplicate files as exact byte-for-byte copies (`shutil.copy`) of the original rather than retyping the content. | Closed — fixed and verified 2026-07-02 |
| I6 | 2026-07-05 | The automated test suite (`test_phase3_4_45.py`) sent **real SendGrid alert emails** to the live recipient list during the Phase 8 Definition-of-Ready run. The Phase 5 snapshot-write-failure negative tests exercise the real `alert_on_error → send_alert` path, and `send_alert()` only short-circuits when `SENDGRID_API_KEY` is unset — so on a machine where the key **is** set (the dev box), those tests emailed both recipients on every run. Four messages were received; the mangled sender address on two of them (`nadeemmarshman_at_gmail.com_narshman@duck.com`) was a **DuckDuckGo Email Protection relay rewrite** on the copy forwarded via the `@duck.com` address — confirmed by the `Duck-Original-From` header — **not** an agent bug. | Test-isolation gap in the same family as **Issue I5**: a code path with a real external side effect (network email) was neither stubbed nor key-cleared, unlike the alert-*content* tests which intercept `send_alert` and set a fake key. Environment-dependent, so it stayed invisible on machines without a live key set (e.g. the sandbox where the suite was first verified). | Cleared `SENDGRID_API_KEY` from the environment at the top of `test_phase3_4_45.py` (`os.environ.pop("SENDGRID_API_KEY", None)`), so no code path in the suite can reach the real send. The real `send_alert` is preserved so `test_unit_send_alert_missing_sendgrid_key` still validates its graceful-degradation path, and the alert-content tests are unaffected (they install their own capture). Verified 2026-07-05: full 45-test suite re-run green with the guard, and the snapshot-failure tests now log "SENDGRID_API_KEY … not set" instead of sending. Motivates a new test-suite **hermeticity** standing rule (no real filesystem, network, or credentials in automated tests). | Closed — fixed and verified 2026-07-05 |
| I7 | 2026-07-05 | The live `SENDGRID_API_KEY` value was exposed in an assistant chat transcript: `os.environ.pop("SENDGRID_API_KEY", None)` was run **interactively in the Python REPL**, which echoed the popped secret as the expression's return value. | The interactive REPL prints the value of the last evaluated expression; `os.environ.pop()` returns the removed value. A line written for a module (where the return value is discarded) leaked the secret when pasted into a live prompt. Realisation of **Risk R5** (credential exposure), extended to the SendGrid API key itself. | Key treated as compromised: rotation steps provided (revoke old key in SendGrid; issue a new **Mail Send-only**, least-privilege key; set `SENDGRID_API_KEY` via a masked `Read-Host -AsSecureString` / `Get-Credential` prompt so the value never enters shell history; restart the terminal). | I8 | 2026-07-14 | Stray Git repository found initialised in the Windows user-profile folder (`C:\Users\{{owner}}`) — a `git init` run from the wrong directory during an assisted session outside this Project. Zero commits, but it offered to track the entire profile (registry, browser data, OneDrive tree, personal documents) — one `git add .` from staging personal data. | Ungoverned-session side effects (same family as I1 and the A7–A9 drift). No commits, no data exposed. Practice reaffirmed: never `git add .`; always work from a terminal opened in the repo. | Closed |
| I9 | 2026-07-15 | The committed §8.3 manifest-export command (`Export-Csv` without `-Encoding UTF8`) silently corrupts unicode filenames in the CSV on Windows PowerShell 5.1 — caught at CP1 via the unicode-filename test case appearing as literal `?` characters in the CSV data. | Windows PowerShell 5.1's default `Export-Csv` encoding is not UTF-8; the spec command was written and committed without an explicit encoding, and no test case had exercised a unicode filename through the export until CP1. | CP1 manifest re-exported with `-Encoding UTF8` and verified clean (2026-07-15). Spec corrected in `TEST_BED_AND_CASES.md` v2.1 (committed and live-verified 2026-07-17): `-Encoding UTF8` on all three checkpoint exports, plus the previously-missing hash-grouping command and a real expected-output example. | Closed — fixed at CP1 2026-07-15; spec correction committed 2026-07-17 |
